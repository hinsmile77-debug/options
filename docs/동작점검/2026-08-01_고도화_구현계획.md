1. **만기유동성 분할을 "레그 평면 슬라이스"가 아니라 "북 단위"로** — 레그를 쪼개면 10분간 부분

   (이건 §4 우선순위 1에서 이미 반영됐고 이 계획서의 5-2와는 무관하다.)

3. **커버리지 정의를 둘로 분리** — 계획서에는 하나로 적었으나 실제로는 분모가 다른 두 지표다:
   북 사이 상대 비교용(분모 = 옵션체인이 실제로 돈 분)과 절대 커버리지(분모 = 경과 분).
   섞으면 위클리가 "55%"인지 "100%"인지가 뒤집힌다.

## 3. §5-2 — `daily_ops_report.py` (본체)

### 왜 지금인가
07-31 보고서 작성에 쓴 집계는 **10회째 손으로 재작성한 것**이다. 게다가 이번엔 신규 집계 3종
(버스트 점유 시간, 창 안 타폴러 호출 실측, 연속 지연 에피소드)이 더 필요했다. 조사 시간의
약 8할이 "표 만들기"였고 "델타를 해석하기"는 2할이었다.

### 3-1. 모듈 배치 — 로직은 `mahdi/ops/`, 스크립트는 얇게

```
mahdi/ops/__init__.py
mahdi/ops/log_metrics.py     # 순수 파서: 로그 라인 이터러블 → 지표 dict   (pytest 100%)
mahdi/ops/db_metrics.py      # SQL 집계: (conn, date) → 지표 dict
mahdi/ops/hypotheses.py      # 가설 파일 로드 + 예측 대조 (§5-1, Phase 3)
mahdi/ops/report.py          # 순수 렌더러: 지표 dict → 마크다운
scripts/daily_ops_report.py  # CLI (인자 파싱 + 파일 I/O만)
```

**이 분리를 택한 이유**: `scripts/log_marketclose_stop.py`가 이미 같은 규약을 문서로 남기고
있다 — *"배치파일이 한 줄로 호출하기만 하면, 실제 로직은 파이썬(pytest로 테스트됨) 쪽에 있어
같은 위험이 없다."* 파서를 `scripts/`에 두면 테스트가 어려워진다.

`log_metrics.py`와 `report.py`는 **순수 함수**(파일 I/O 없음)로 유지한다 — 로그 픽스처 문자열과
지표 dict만으로 전부 검증 가능하다.

### 3-2. 입력 해석 — 로그 로테이션 처리 (설계상 가장 까다로운 부분)

`observation_loop.log`는 10MB/10개 로테이션이다(`LOG_MAX_BYTES`/`LOG_BACKUP_COUNT`).
**하루치가 `.log`와 `.log.1`에 걸쳐 있는 경우가 실제로 있었다**(07-30이 그랬다).

```python
def iter_day_lines(log_dir: Path, target: date) -> Iterator[str]:
    """observation_loop.log{,.1,..,.10}을 오래된 것부터 훑어 target 날짜 줄만 흘려보낸다."""
```

- 오래된 파일부터(`.log.10` … `.log.1`, `.log`) 순회해 **시간순**을 보장한다.
- 줄 단위 스트리밍(전체를 메모리에 올리지 않는다 — 과거 105MB 파일 전례가 있다).
- **트레이스백 연속 줄은 타임스탬프가 없다** — 직전 타임스탬프 줄의 날짜를 승계한다
  (이 처리를 빠뜨리면 ZN/ES 트레이스백이 통째로 누락돼 "로그 볼륨" 집계가 틀린다).
- 대상 날짜 줄이 한 줄도 없는 파일은 **첫 줄만 읽고 건너뛴다**(전체 스캔 방지).

## 5. §5-1 — "예측 → 실측 검정"을 표준 절차로

### 배경
07-31 §2-0의 "가설 8개 검정" 표가 가능했던 유일한 이유는 **07-30 세션이 NEXT_TODO에 검증
항목을 남겨뒀기 때문**이다. 08-01 세션도 같은 형태로 남겼다(08-03 검증 항목 6종).
지금은 이게 **사람의 습관**에 의존한다.

### 작업 — 기계 판독 가능한 가설 파일 + 자동 대조

`docs/동작점검/hypotheses.yaml` (단일 누적 파일):

```yaml
- id: "2026-08-01-p1-expiry-burst"
  구현일: 2026-08-01
  검증예정일: 2026-08-03
  가설: "만기유동성 버스트를 북별 홀수분 슬롯으로 나누면 mod10=2 충돌이 사라진다"
  예측:
    - metric: foreign_calls_in_window.mod10_2   # log_metrics가 내는 키와 동일해야 함
      expect: "<= 1.0"
    - metric: overrun_count.mod10_2
      expect: "<= 5"
  상태: pending      # pending | confirmed | refuted | inconclusive
```

`mahdi/ops/hypotheses.py`:
- YAML 로드 → 그날 지표 dict에서 `metric` 경로를 찾아 **실측치와 나란히 렌더링**
- `expect`는 `<=`, `>=`, `==`, `A~B`(범위)만 해석한다. 해석 불가하면 **판정하지 않고 두 값만
  나란히 보여준다**(억지 자동 판정보다 낫다)
- 판정 결과를 리포트 `§0. 가설 검정` 절로 낸다. **파일의 `상태`는 자동으로 고치지 않는다** —
  사람이 보고서를 쓰면서 손으로 바꾼다(자동 판정이 틀렸을 때 조용히 덮이는 것을 막는다)

### 규약 (문서화)
`docs/동작점검/README.md`를 신설해 한 문단으로 못박는다:
> **fix를 구현하는 세션은 그 자리에서 `hypotheses.yaml`에 예측치를 적는다.** 다음 거래일
> 리포트가 자동으로 대조해준다. 예측치를 못 적겠으면 그 fix는 아직 근거가 부족한 것이다.

마지막 문장이 이 항목의 진짜 가치다 — 07-30의 *"밀린 데이터는 어차피 유실"* 이라는 추론이
예측치 형태로 강제됐다면 그날 바로 걸렀을 것이다.

**예상 규모**: `hypotheses.py` ~120줄 + 테스트 + YAML 초기 항목(08-03 검증 6종) + README.

## 6. §5-4 — 안전장치 생존 신호, 남은 3개 후보

> 원칙(08-01 DECISION_LOG에 기록됨): **생존 신호는 감시 대상과 독립한 타이머에서 나와야 한다.**
> CB 감지에는 적용 완료. 아래 셋은 미적용.

### 6-1. `CircuitBreaker`(내부 킬스위치) — 가장 시급

**현재 상태**: 라이브 루프에서 **한 번도 `evaluate()`되지 않는다.** 일간 래치 설계라 매분 부르면
의도치 않게 HALTED로 고착될 수 있어 **일부러 안 부른 것**이고, `risk_snapshots.cb_state`의
`circuit_breaker_state_is_last_evaluated: true` 플래그가 그 사실을 정직하게 표시하고 있다.

문제는 그 결과 **킬스위치가 살아있는지 아무도 모른다**는 것이다 — CB 감지와 정확히 같은 상황.

**설계**:
1. `CircuitBreaker.evaluate_readonly(account_state, market_conditions) -> CircuitBreakerDecision`
   추가 — 조건을 전부 평가하되 `_state`/`_halt_reasons`를 **변경하지 않는다**.
2. **`evaluate()`를 `evaluate_readonly()` 위에 다시 얹는다** — 평가 로직을 한 곳에만 두고
   `evaluate()`는 그 결과로 상태만 갱신한다.
   > **이게 필수 전제다.** 두 경로가 갈라지면 "평가된 것과 실제 동작이 다르다"는 지금보다
   > 나쁜 상태가 된다.
3. `poll_signal_fusion_cycle`이 매 사이클 `evaluate_readonly()`를 호출해 `risk_snapshots.cb_state`에
   **실제 조건 평가 결과**를 남긴다(`..._is_last_evaluated` 플래그는 제거).
4. 배지: `킬스위치 평가 HH:MM:SS · 발동조건 0/5` — 평가 시각이 오래되면 경고.

**리스크**: `evaluate()` 리팩터가 기존 리스크 테스트를 건드린다. → 리팩터 전후로
`tests/test_risk_circuit_breaker.py`가 **한 줄도 안 바뀌고 통과**하는 것을 조건으로 삼는다.

### 6-2. `RiskEngine` 거부 경로

**현재 상태**: 07-31에 **0회 호출**(진입 후보가 없으면 안 불린다).

6-1을 넣으면 `evaluate_entry`의 앞단(`market_halt` → `circuit_breaker`)은 사실상 매분 평가된다.
나머지(한도 체계·사이징)는 진입 후보가 있어야 의미가 있으므로 **억지로 매분 부르지 않는다**.

**설계**: `risk_snapshots`에 "오늘 `evaluate_entry` 호출 횟수 / 마지막 호출 시각"을 남기고
COCKPIT이 표시한다.
> **0회에 경고를 걸지 않는다.** 진입 후보가 없었다는 정상 상태다. 여기에 임계를 두면
> CB 하트비트와 똑같은 실수(정상을 이상으로 표시)를 반복한다. **정보 배지로만 둔다.**

### 6-3. WS 재연결 감지

**현재 상태**: 07-31 재연결 **0회** — 재연결 로직이 살아있는지 증명되지 않았다. WS 수신 자체는
`market_raw_1m` 적재로 간접 증명되지만 그건 "재연결 감지"가 아니다.

**설계** (CB 감지와 같은 패턴):
- 마이그레이션 020: `ws_status` 싱글턴 — `connected_since`, `last_message_at`,
  `reconnect_count_today`, `updated_at`(**독립 300초 하트비트**가 갱신).
- `poll_ws_heartbeat()` 태스크가 `run_observation_loop_forever`가 들고 있는 연결 상태 객체를
  읽어 300초마다 upsert.
- 배지: `WS 연결 HH:MM:SS부터 · 오늘 재연결 N회 · 최근 수신 HH:MM:SS`.
- `updated_at`에는 임계를 걸고, `last_message_at`에는 **장중에만** 임계를 건다
  (장외에는 체결이 없어 정상적으로 비어 있다).

**예상 규모**: 6-1 리팩터 + 배선 ~120줄, 6-2 ~60줄, 6-3 마이그레이션 + 태스크 + 배지 ~180줄,
테스트 합계 ~250줄.
