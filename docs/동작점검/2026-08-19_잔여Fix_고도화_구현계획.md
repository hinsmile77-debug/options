## §5. 자동 수행 설계 — 실수 없이 돌리려면

### 5-1. 항목당 **6단계 고정 루프**. 단계를 건너뛰면 그 항목은 실패로 친다

```
(1) 착수 전 코드 검증   보고서가 지목한 파일·줄·심볼이 지금도 그런가.
                        어긋나면 「구현」 대신 「폐기 사유」를 쓰고 다음 항목으로 간다.
                        ← 08-18 Fix#1이 이 단계에서 걸렸다. 이 계획에서 가장 값진 단계다.
(2) 예측치 선등재       숫자를 보기 전에 hypotheses.yaml. 주장 1건 + 대가 1건 필수(규약 E).
(3) 회귀 테스트 먼저    실패하는 테스트를 먼저 쓴다. 테스트 이름이 이 항목의 「완료」 정의다.
(4) 구현                최소 변경. 새 상수·새 라벨은 기존 것을 못 쓸 때만.
(5) 검증                uv run pytest -q (전체) + ruff. 부분 실행으로 끝내지 않는다.
(6) 단독 커밋           [MW0601] 태그. 본문에 「무엇을 재는가 / 대가 / 언제 판정되는가」.
```

### 5-2. 중단 규칙 — **한 항목이 죽어도 전체를 멈추지 않는다**

- (5)에서 실패하면 **그 항목만** `git checkout -- <files>`로 되돌리고 다음 항목으로 간다.
  넷 중 셋이 들어가는 편이 넷 다 안 들어가는 것보다 낫다.
- **단, 0단계가 실패하면 전부 중단한다.** 더러운 트리 위의 커밋은 되돌리기가 어렵다.
- 09:00을 넘기면 **남은 항목은 15:20 이후로 미룬다**(장중 편집 금지).

### 5-3. 병렬화 — **권하지 않는다**

네 항목 중 **셋이 `report.py`/`log_metrics.py`/`hypotheses.py`를 공유**한다. 서브에이전트로 갈라
동시에 편집하면 충돌 해소 비용이 순차 실행 시간을 넘고, 무엇보다 **(5) 전체 테스트가 서로의 변경을
섞은 상태로만 돌 수 있다** — 실패했을 때 누구 탓인지 못 가른다. **순차 1→2→3→4가 옳다.**

### 5-4. 자동 실행이 **넘지 말아야 할 선** 셋

1. **`hypotheses.yaml`의 `상태:`를 자동으로 바꾸지 않는다.** 확정은 사람이 한다(파일 머리 규약).
   오늘 작업은 항목 **추가**와 **경로 정정**까지다.
2. **`dev_memory`는 초안까지만.** `DECISION_LOG.md`·`NEXT_TODO.md` 갱신은 사람 검토 후.
   다만 완료 사실을 아무 데도 안 남기면 내일 세션이 또 §4를 위에서부터 읽는다 —
   **완료는 커밋 본문에 남기고, `NEXT_TODO` 반영은 초안으로 제시한다.**
3. **cron·클라우드 루틴은 건드리지 않는다**(Fix#7). 사용자 승인 후에만.

### 5-5. 완료 판정 — 다음 셋이 전부 참일 때만 「끝」이라고 쓴다

- `uv run pytest -q` → **1,729 + 신규 테스트 수** 전부 통과, 신규 ruff 위반 0
- 오늘 등재한 예측치가 **주장·대가 각 1건 이상**을 갖는다
- 08-20 리포트에서 볼 지표 경로가 **오늘 만든 린트를 통과한다**(자기 자신에게 먼저 적용한다)
