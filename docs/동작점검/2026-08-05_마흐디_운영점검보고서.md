**21건이 창 밖, 1건만 창 안.** 그리고 창 밖 21건의 `flip/spot` 비율이 전부
**0.95~0.99 구간에 몰려 있다** — 이것이 결정적 단서다.

`mahdi/features/options_intel.py:270`
```python
step_size = (spot * 2 * search_pct) / (steps - 1)     # search_pct = 0.05
grid = [spot * (1 - search_pct) + i * step_size for i in range(steps)]
```

탐색 그리드는 **스팟 ±5%(스팟 1040이면 988~1092, 폭 104포인트)**인데, 실제 수집 레그는
**ATM±2 = 5행사가 = 폭 10포인트**다. **그리드의 90%가 레그가 하나도 없는 구간이다.**
그 구간에서 모든 레그의 BS 감마는 사실상 0으로 수렴하고, `gex_at(S)`는 부동소수 잔여에
불과해진다 — 부호가 아무 이유 없이 바뀐다. 그 첫 교차점이 **그리드 왼쪽 끝 근처**에서
잡히므로 `flip ≈ 0.95 × spot`이 반복해서 나온다.

docstring은 실패 조건을 *"그리드 전 구간에서 부호가 바뀌지 않으면 None (flip 레벨이
**탐색 범위** 밖 — 정상적인 결과)"*라고 적는다. **탐색 범위는 검사하지만 레그 범위는
검사하지 않는다.** 08-04에 고친 "허수 flip"(`v_prev == 0`이면 그리드 왼쪽 끝 반환)과
**같은 자리에서 다른 경로로 재발했다.**

**피해**: 08-04 Fix#3(`OPTIONS_FLOW_GAMMA_WALL_FALLBACK`)은 *"flip이 None이면 감마월로
대체"*한다. 즉 **flip이 None인 472분은 옳게 감마월을 썼고, flip이 있는 22분만 허수를
기준점으로 삼았다.** 옵션 축 신호가 하루 22번 근거 없이 뒤집힌 것이다.

> **08-04 §2-3의 결론 *"감마플립 0%는 결함이 아니라 시장 구조"*는 여전히 옳다.**
> 오늘 0%가 아니게 된 것은 시장이 바뀌어서가 아니라 **탐색 그리드가 레그 없는 허공을
> 훑었기 때문**이고, 자동 리포트 §15의 「광폭 감마플립」은 오늘도 세 북 모두 **없음**이다.
> §15(방문 전 행사가 기준, 없음)와 §14(라이브 스냅샷 기준, 22건)가 **서로 모순되는
> 답을 내고 있었는데 아무도 둘을 나란히 읽지 않았다.**

#### §2-6 【신규】 옵션체인이 **0행인 분이 4개인데 결손 지표는 1분**을 보고했다

자동 리포트 §4:
```
결손 1분 (홀수분 0 / 짝수분 1) → 미회수 1분
10:04
```

DB 실측(07:31~15:44 전 분에 대한 `option_analysis_1m` 존재 여부):

```
10:04:00   행 0
10:54:00   행 0     ← 리포트에 없음
12:57:00   행 0     ← 리포트에 없음
14:31:00   행 0     ← 리포트에 없음
```

그리고 반대쪽 이상도 있다 — **설계 상한 20행을 넘는 분이 2개**(22행 1개, 24행 1개).
그중 12:56은 **22행**이고 바로 다음 분 12:57이 **0행**이다.

원인이 둘로 갈린다.

- **14:31은 명백하다.** 로그: `옵션체인 수집 예산(50초) 초과 — 남은 7레그를 포기하고
  **0레그**로 이번 분을 마감합니다` → `rows=0`. **사이클은 정상 실행됐고 데이터만 전멸했다.**
  결손 지표는 *"사이클이 안 돌았는가"*를 세므로 이 분을 **구조적으로 못 본다.**
- **10:54 / 12:57은 다르다.** 로그상 두 분 모두 사이클이 돌아 `rows=19`를 남겼는데
  DB의 그 분에는 행이 없고, 인접 분(12:56)이 22행으로 부풀어 있다. **그 사이클의 행이
  이전 분 타임스탬프로 적재됐다** — 즉 `option_analysis_1m`의 분 라벨이 그 행을 만든
  사이클과 항상 일치하지는 않는다. 로그(사이클 관점)와 DB(분 라벨 관점)가 어긋나는
  경로가 있고, 결손 지표는 로그 쪽만 본다.

> 08-04 Fix#8이 도입한 예산은 **"데이터 일부를 버려 시간을 지킨다"**는 거래였고 그 자체는
> 옳다. 문제는 **그 거래의 대가를 세는 계측이 예산 도입과 함께 만들어지지 않았다**는 것이다.
> `overrun.count`(밀림)는 0으로 훌륭한데, 밀림이 0인 이유의 일부가 **데이터를 버렸기 때문**
> 이라는 사실이 결손 지표에는 안 나타난다. **07-31 §5-5 원칙("인프라 지표가 좋아져도 판단
> 입력은 나빠질 수 있다")의 세 번째 재발이다.**

## 5. Fix 구현 계획

우선순위는 **(a) 판단이 허수를 먹는 것을 끊고 → (b) 데이터 손실을 보이게 하고 →
(c) 계측 오염을 제거** 순이다. 판단 파이프라인이 오늘 처음 살아났으므로, **그 입력에
섞인 거짓을 먼저 끊는다.**

### Fix#1 【최우선】 감마플립을 레그 범위 안으로 가둔다 (§2-5)

`find_gamma_flip()`이 **레그가 실재하는 구간에서만** flip을 인정하게 한다.

```python
# mahdi/features/options_intel.py
strikes = [leg.strike for leg in usable]
lo, hi = min(strikes), max(strikes)
# 그리드는 지금처럼 스팟 ±5%로 두되(외삽 자체가 정보이므로 그리드는 좁히지 않는다),
# 부호 전환 구간 [grid[i-1], grid[i]]가 [lo, hi]와 겹치지 않으면 flip으로 인정하지 않는다.
```

- 경계값 선택 근거: 오늘 유일하게 창 안이던 15:17(flip 1042.33, 창 1040~1050)은 통과하고
  나머지 21건은 전부 걸린다.
- **거부 사유를 로그와 `signal_decisions`에 남긴다** — `flip_rejected_out_of_leg_range`.
  조용히 None으로 떨어뜨리면 08-03 이전(넉 달간 무음)과 같은 상태가 된다.
- `find_gamma_flip`의 docstring 실패 조건을 *"탐색 범위 밖"* → *"**레그 범위** 밖"*으로
  고친다. 지금 문서가 검사하지 않는 것을 검사한다고 적고 있다.
- 리포트 §14의 「감마플립 산출률」 옆에 **「그중 레그 범위 안」**을 병기한다. 오늘 값은
  `4.5% (그중 창 안 0.2%)`로 찍혀야 한다.

**예측(`2026-08-06-p1`)** — 주장 지표를 맨 앞에 둔다:
`db.signal_reach.gamma_flip_in_leg_range_pct` **≤ 1%**(주장 지표),
`db.signal_reach.gamma_flip_pct` ≤ 1%. **둘 다 0이어도 정상이다** — 08-04 §2-3이
확정했듯 이 북에 flip은 구조적으로 없다.

### Fix#2 【데이터 손실 가시화】 결손 지표를 DB 기준으로 이중화한다 (§2-6)

지금 결손은 **로그(사이클 실행 여부)** 한 축뿐이다. **적재 결과** 축을 추가한다.

- `mahdi/ops/db_metrics.py`에 `chain_minute_coverage(conn, date)` 신설:
  경과 분 대비 `option_analysis_1m`에 행이 **1개 이상 있는 분**의 비율, 그리고
  **0행 분 목록**. 오늘 값은 `4분 (10:04 / 10:54 / 12:57 / 14:31)`.
- 리포트 §4를 **「결손 분(로그 기준)」과 「0행 분(DB 기준)」 두 줄**로 낸다.
  **두 값이 다르면 그 차이 자체를 ⚠로 낸다** — 오늘이라면 `로그 1분 vs DB 4분 ⚠`.
- `rows=0`으로 끝난 사이클은 예산 초과 WARNING과 **별개의 ERROR**로 올린다. 지금은
  17레그로 마감한 분과 0레그로 마감한 분이 같은 레벨·같은 문구다.
- 부수 조사(별건, 예측 없이): 12:56이 22행인 경로. **`option_analysis_1m`의 분 라벨이
  어느 시각에서 오는지**를 확정하고 테스트로 고정한다. 이것이 §2-6 후반의 근본 원인이다.

**예측(`2026-08-06-p2`)**: `db.chain_minute_coverage.zero_row_minutes` **≥ 1건 보고됨**
(주장 지표 — **0건이 나오면 지표가 안 붙은 것**이지 손실이 사라진 것이 아니다.
08-04에 `slow_calls 0건`을 개선으로 읽은 실수를 반복하지 않는다).

### Fix#3 【판단 입력 보호】 먼슬리 레그 완전성을 잰다 (§2-7)

> **⚠ 이 항목의 초안 전제는 틀렸다 — 구현 착수 시점에 코드를 읽고 정정했다.**
> 초안은 *"수집 순서에 만기 우선순위가 없다"*고 적고 순서 변경을 제안했다. 실제로는
> `books`가 이미 `[(먼슬리,'regular'), (위클리월), (위클리목)]` 순이고
> `_books_due_this_cycle()`이 그 순서를 보존한다(docstring도 그렇게 단언한다).
>

### 고도화#1 「지표는 감시 대상과 **독립한 입력**을 써야 한다」를 규약으로 승격
