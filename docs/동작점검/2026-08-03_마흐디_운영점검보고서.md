### 2-1. [핵심/신규] 감마플립이 **전 이력에서 한 번도 계산된 적이 없다** — NaN 오염

**가장 심각한 발견이다.** 라이브 DB로 `find_gamma_flip()`을 그대로 재현한 결과:

```
전체(현행 246레그)         : nan=41/41  부호종류=set()  → flip=None
먼슬리만(83레그, t_years 정상): nan=41/41  부호종류=set()  → flip=None
당일만기(24레그)            : nan=41/41  부호종류=set()  → flip=None
```

**41개 그리드 포인트가 전부 NaN이다.** 어느 부분집합을 넣어도 마찬가지다.

**원인.** `options_intel.py:105~110`의 `gex_at(s)`는 레그별 BS 감마를 단순 합산한다.

```python
for leg in legs:
    g = _bs_gamma(leg.option_type, s, leg.strike, leg.t_years, risk_free_rate, leg.iv)
    total += _CALL_PUT_SIGN[leg.option_type] * g * leg.oi * multiplier * s_term
```

`leg.iv == 0`이면 BS의 d1에 0-나눗셈이 생겨 `g`가 NaN이 되고, **NaN이 하나라도 더해지면 `total`
전체가 NaN**이다. 오늘 먼슬리 체인만 봐도 `iv=0` 레그가 3개, 전체로는 15개다. DB 원본 기준으로도
`option_analysis_1m`의 오늘 행 중 iv가 0/NULL인 것이 먼슬리 215행(4.4%)·weekly_mon 237행(9.7%)이다.

그리고 NaN은 부호 비교를 **조용히** 무력화한다:

```python
if values[i - 1] * values[i] < 0:   # NaN * NaN < 0  →  항상 False
```

예외도 경고도 없이 루프를 끝까지 돌고 `return None`한다.

**docstring이 이 상황을 정확히 반대로 서술하고 있다.**
> *"그리드 경계(t_years/iv≈0)에서 나는 0-나눗셈 RuntimeWarning도 같은 이유로 억제(값 계산 자체는
> 정상, numpy가 nan/inf를 반환할 뿐이고 **그 지점은 그대로 GEX 부호 비교에 들어가 flip 계산에
> 영향 없음**)"*

"그 지점만" 오염되는 게 아니라 **합계를 거쳐 전 구간이 오염된다.** RuntimeWarning 억제가 이 사실을
6개월 가까이 덮어왔다.

**파급.** `_options_flow_score()`는 `gamma_flip`이 None이면 (charm 미배선 상태에서) `None`을 반환한다.
→ 앙상블 멤버 `options_flow`가 항상 미가용. `signal_decisions` **전수 조회**로 확인:

| 날짜 | available_member_count | 건수 |
|---|---|---|
| 2026-08-03 | 2 / 1 | 419 / 75 |
| 2026-07-31 | 2 / 1 | 418 / 77 |
| 2026-07-30 | 2 / 1 | 419 / 75 |
| 2026-07-29 | 2 / 1 | 418 / 76 |
| 2026-07-28 | 1 | 8 |

**3 이상인 행이 0건이다.** 6개 멤버 중 `xgboost_tabular`/`lstm_temporal`은 설계상 미학습이고,
`orderflow_ofi_vpin`은 OFI/큐임밸런스 파이프라인 미구현이라 항상 None이다(`main.py:2211~2212`에서
명시적으로 `ofi=None, queue_imbalance=None`). 그러면 남는 후보는 `regime_hmm`·`options_flow`·
`flow_position` 셋인데, 실측 2 = **regime_hmm + flow_position(외국인 순매수 부호)뿐이다.**

즉 **오늘 419분의 판단은 "레짐(항상 0.0, RANGE_BALANCED는 방향 무의미) + 외국인 순매수 부호"
두 개로만 내려졌다.** 옵션 시스템인데 옵션 신호가 없다.

> 장전 75분이 amc=1인 것은 정상이다 — 투자자수급 데이터가 아직 없어 `flow_position`도 없다.

### 2-2. [핵심/신규] `latest_option_chain()`에 시간 범위도 만기 필터도 없다 — 4주치 유령 레그

`db.py:657`의 쿼리는 이렇다:

```sql
SELECT DISTINCT ON (strike, option_type) ...
FROM option_analysis_1m
WHERE underlying=%s
ORDER BY strike, option_type, timestamp DESC
```

`WHERE`에 **시각 조건이 없고 만기 조건도 없다.** ATM±2 창은 스팟을 따라 움직이므로, 한때 창 안에
있다가 빠져나간 행사가는 **그때의 값 그대로 영원히 스냅샷에 남는다.**

오늘 15:45 시점 실측:

| 구분 | 값 |
|---|---|
| 반환 레그 수 | **246** |
| 그중 **오늘** 수집분 | **10** |
| 만기 종류 | **11종** (2026-07-06 ~ 2026-08-13) |
| 이미 만기가 지난 레그 (`t_years=0`) | **156 / 246 (63%)** |
| 가장 오래된 레그의 timestamp | **2026-07-06 10:45** (4주 전) |

수집 시각별 분포: `07-06:46, 07-10:36, 07-28:30, 07-29:18, 07-07:14, ... , 08-03:10`

**GEX 실측 비교** (spot 986.72):

| 입력 | GEX |
|---|---|
| 전체(현행) | **-563억** |
| 미만기만(expiry ≥ today) | -155억 |
| 먼슬리만(2026-08-13) | -243억 |
| 오늘 수집분만 | **+28억 (부호가 반대)** |

**부호가 뒤집힌다.** GEX 부호는 v6 §7의 "+GEX 회귀장 / −GEX 증폭장" 판정과 §11.4 프리미엄 매도
게이트(`positive GEX` 요구)의 입력이다. 현행 값으로 Phase 2 진입 판정을 하면 **정반대 전략을
허용**하게 된다.

**이 설계가 의도된 것이 아니라는 증거 두 가지:**

1. `options_intel.py:42` docstring — *"만기가 지난(또는 없는) 레그는 제외한다"* 고 적혀 있으나
   코드는 `if row.get("expiry") is not None`만 건다(`options_intel.py:56`). **문서-코드 불일치.**
2. `main.py:120` 주석은 위클리 격분 전환 근거로
   *"`DISTINCT ON`으로 레그별 최신값을 취하므로 위클리를 안 조회한 분에는 직전 값이 그대로 이월돼
   체인 스냅샷에 구멍이 생기지 않는다"* 고 적었다. **이월 자체는 맞지만 이월 기간에 상한이 없다는

**(b)(c) z-score 폭발 — 드라이런이 정확히 잡으라고 만든 종류의 결함**

`fit_regime_engine.py --dry-run`을 08-10 임계 도달 **전에** 돌린 결과, `fit()`은 예외 없이 끝나는데
**6회 재시작이 전부 "Model is not converging"**(로그우도 −2.2e22)이었다. 진단을 붙여 보니:


> **이것이 NEXT_TODO가 드라이런을 요구한 이유 그 자체다** — *"08-10에 처음 돌려서 실패하면 또

수정 후: 로그우도 **−2.2e22 → +22,383**, cross_asset_stress **1e12 → 8.98**,

### 우선순위 1 — 감마플립 NaN 오염 제거 + 체인 경계 + **ATM 재롤링** (§2-1, §2-2, §4-0a) ✅

**이 두 개는 같은 커밋으로 간다** — 하나만 고치면 다른 하나가 여전히 신호를 망친다.

#### (a) `find_gamma_flip()` — 못 쓰는 레그를 계산 전에 배제하고, NaN을 삼키지 않는다

`mahdi/features/options_intel.py`

```python
def _usable_for_bs(leg: OptionLeg) -> bool:
    """BS 감마를 계산할 수 있는 레그인가 — iv/t_years/strike가 전부 양수여야 한다.
    2026-08-03 §2-1: iv=0 레그가 하나만 섞여도 gex_at()의 합계 전체가 NaN이 되고,
    NaN은 `values[i-1]*values[i] < 0`을 항상 False로 만들어 flip이 조용히 None으로 떨어진다
    (전 이력 0건 산출의 원인). RuntimeWarning 억제가 이 사실을 덮고 있었다."""
    return leg.iv > 0 and leg.t_years > 0 and leg.strike > 0
```

- `find_gamma_flip()` 진입부에서 `legs = [l for l in legs if _usable_for_bs(l)]`
- 필터 후 남은 레그가 `_MIN_FLIP_LEGS`(=6, 행사가 3개 × C/P) 미만이면 `None` + **WARNING 1줄**
  (`WarningThrottle`로 60초 1건) — 지금처럼 조용히 사라지지 않게 한다.
- `values`에 NaN이 남아 있으면(방어) 그 지점을 건너뛰고, 전부 NaN이면 WARNING.
- **docstring의 잘못된 서술을 고친다**(*"영향 없음"* → *"합계 전체를 오염시키므로 사전 배제한다"*).

#### (b) `latest_option_chain()` — 시간 창과 만기 경계를 건다

`mahdi/data/db.py:657`

```sql
SELECT DISTINCT ON (expiry, strike, option_type)
       strike, option_type, oi, iv, gamma, gex, expiry, timestamp
FROM option_analysis_1m
WHERE underlying = %s
  AND timestamp >= %s          -- now - CHAIN_SNAPSHOT_MAX_AGE (기본 10분)
  AND expiry   >= %s           -- 오늘 이후(당일 만기 포함)
```

- **`DISTINCT ON`에 `expiry`를 추가**한다 — 지금은 만기가 다른 3북이 같은 행사가에서 서로를

- 파라미터는 상수로 노출한다(`CHAIN_SNAPSHOT_MAX_AGE_MINUTES = 10`).
- **`option_chain_as_of()`도 같은 규칙으로 맞춘다**(백테스트와 라이브가 다른 체인을 보면 안 된다).

#### (c) 회귀 테스트

- `iv=0` 레그를 섞은 체인에서 `find_gamma_flip()`이 **값을 돌려주는지**(현행 코드로는 반드시 실패).

## 5. 고도화 방안 — **6종 전부 구현 완료(같은 세션)**

### 5-1. "관측 품질" 지표를 **판단 입력 한 칸 아래까지** 내린다

07-31 §5-5가 세운 원칙은 옳았다 —
> *"인프라 지표(밀림·백오프)가 좋아져도 판단 입력은 나빠질 수 있으므로 반드시 나란히 읽는다."*

그래서 "먼슬리 분 커버리지"를 만들었고, 오늘 그것이 98.8%로 훌륭하게 나왔다.
**그런데 감마플립은 0%였다.** 커버리지는 *"데이터가 DB에 있는가"* 만 재고, *"그 데이터가 신호까지
도달했는가"* 는 안 잰다. 한 칸이 비어 있었다.

`mahdi/ops/db_metrics.py`에 **"신호 도달률" 블록**을 추가한다 — 자동 리포트 §13에 나가고,
COCKPIT "관측 품질" 배지와 계산 함수를 공유한다(README의 규약: 리포트와 배지가 다른 답을 내면 안 된다).

| 지표 | 계산 | 오늘 값 | 경고 임계 |
|---|---|---|---|
| **앙상블 멤버 가용률** | `available_member_count` 분포 | 최대 2 / 이론 최대 4 | 최대값 < 3 |
| **감마플립 산출률** | flip이 not-null인 분 / 장중 분 | **0%** | < 80% |
| **체인 스냅샷 신선도** | 최고령 레그 age 중앙값 | **40,000분** | > 15분 |
| **체인 스냅샷 레그 수** | `latest_option_chain()` 반환 수 | **246** | 예상(30) ±50% 이탈 |
| **피처 중립값 탈출률** | 피처별 (기존 §13) | rv_ratio 0% | 0%가 2일 연속 |

**이 5개 중 4개가 오늘 경고를 냈을 것이다.** 감마플립 산출률은 별도 저장이 필요하므로
`signal_decisions`에 `gamma_flip` 컬럼(nullable)을 추가한다 — 판단 시점의 입력을 함께 남기면
사후에 "왜 그 판단이었나"를 재구성할 수 있다(지금은 불가능하다).

### 5-2. 판단 축에 로거를 붙인다 — **오늘 하루 로거가 3개뿐이었다**

`httpx` / `mahdi.main` / `mahdi.broker.rest_client`. 그게 전부다.
`ws_client`는 **로거 자체가 없고**, `engines`·`risk`·`fusion`·`features`·`execution`·`learning`은
전부 무음이다.

§2-1의 버그가 몇 달간 안 보인 이유가 정확히 이것이다 — **감마플립이 None으로 떨어져도 아무도 아무
말을 하지 않는다.** 관측 시스템이 자기 자신의 절반을 관측하지 않고 있다.

**최소 침습 원칙**(로그 볼륨을 다시 늘리면 §2-8의 가독성을 또 잃는다):

| 위치 | 무엇을 | 얼마나 |
|---|---|---|
| `fusion/engine.py` | 멤버 가용 조합이 **바뀔 때만** 1줄 | 하루 수 건 |
| `engines/regime_pipeline.py` | 피처가 **중립값을 처음 벗어날 때** 1줄 | 피처당 평생 1건 |
| `features/options_intel.py` | 감마플립 산출 실패가 **연속 N분** 지속될 때 1줄(throttle) | 정상일 0건 |

### 5-3. `hypotheses.yaml` 규약이 효과를 입증했다 — 다만 **"관측 가능성"까지 요구해야 한다**

오늘 13개 예측 중 12개가 자동 대조로 즉시 판정됐다. 규약은 성공이다.

**그런데 §2-1의 버그는 어떤 가설로도 안 잡혔을 것이다** — 아무도 "감마플립이 계산되는가"를
예측치로 적지 않았기 때문이다. 그것이 *당연히 되고 있다*고 가정했다.

`README.md`의 규약에 한 줄을 추가한다:

> **fix가 어떤 값을 "쓰는" 경우, 그 값이 실제로 생산되고 있다는 것을 먼저 예측치로 적는다.**
> "X를 개선한다"의 예측치는 "X가 좋아진다"가 아니라 **"X가 존재한다"에서 시작한다.**
> (2026-08-03 §2-1 — 4개월간 GEX/감마플립을 개선해 왔는데 감마플립은 한 번도 산출된 적이 없었다.)

### 5-4. 자동 지표에 **전일 사이드카 델타**를 붙인다

오늘 리포트는 *"전일 지표 사이드카가 없어 델타를 생략했다"* 로 끝났다 — 최초 실행이라 당연하지만,
그래서 §2-5의 백오프 악화(2.25 → 2.76)를 **사람이 07-31 보고서를 열어 손으로 찾아야 했다.**

내일부터는 사이드카가 있으므로 자동으로 붙는다. 여기에 두 가지를 더한다:

1. **주요 지표의 방향성 표기** — "밀림 -15%"만이 아니라 "밀림 -15% ✅ / 백오프 최대 +23% ⚠"처럼
   개선/악화를 명시한다(어느 쪽이 좋은 방향인지는 지표별 상수로 둔다).
2. **`hypotheses.yaml`에서 검증예정일이 지났는데 `상태: pending`인 항목을 §0 맨 위에 띄운다** —
   지금은 표에 섞여 들어가 놓치기 쉽다. 규약상 사람이 손으로 확정해야 하므로, 확정 안 된 것이
   쌓이면 규약 자체가 무력해진다.

### 5-5. 체인 스냅샷을 **북별로** 다루는 것을 검토한다

§4 우선순위 1(b)에서 `DISTINCT ON`에 `expiry`를 넣으면 3북이 분리된다. 그 다음 단계로,
**GEX/감마플립을 북별로 계산해 나란히 보는 것**을 제안한다.

근거: 오늘은 **weekly_mon 만기일**이었다(2026-08-03). 만기 당일 북은 `t_years=0`이라 BS 감마가
정의되지 않고, 핀 리스크(v6 §A3 "만기 Pinning")는 **바로 그 북에서만** 나온다. 3북을 합산하면
그 정보가 먼슬리 감마에 묻힌다.

- `regular`(먼슬리) → GEX/감마플립/감마월의 **주 입력**(v6 §11.4 게이트)
- `weekly_*` → **핀 리스크 전용** 지표(만기일 당일 ATM 집중도)

이것은 §4 우선순위 1을 끝낸 뒤 **별도 증분**으로 다룬다 — 지금 같이 하면 무엇이 무엇을 고쳤는지
구분할 수 없다.
