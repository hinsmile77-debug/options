## 0. 배경 — 지금 무엇이 문제인가

마흐디는 매 분 세 만기북(`regular`=먼슬리, `weekly_mon`=위클리 월, `weekly_thu`=위클리 목)을
**동시에** 수집한다(`mahdi/main.py` `poll_option_chain`, 옵션 레그 20개 = 먼슬리 10 + 위클리 10).
그런데 종목 선택기(`mahdi/fusion/instrument_selection.py` `select_book()`)는 지금

> 관측된 만기 중 **오늘을 제외한 가장 가까운 만기**를 고른다

는 단 하나의 규칙만 쓴다. 요일도, 실제 시장 거래량도 보지 않는다. 그 결과가 2026-08-18 12:30
장중 점검(§1)에서 드러난 문제다 — 선택기가 고른 북(가장 가까운 위클리)에 전략이 요구하는
델타(0.2~0.3)의 유동성이 없어서, 165건의 후보 탐색 중 163건이 `no_strike_match`로 실패했다.

**가설**: 선택기가 "가장 가까운 만기"가 아니라 "**오늘 시장 거래량이 실제로 몰리는 북**"을
고르면, 유동성이 있는 곳에서 후보를 찾게 되어 이 실패가 줄어든다. 그 가설을 실측으로
검증한 결과가 §1이다.

## 1. 최종 규칙 (우선순위 순서 — 위가 이긴다)

| 순위 | 조건 | 목표 종목 | 근거 |
|---|---|---|---|
| 1 | 오늘이 **어느 북이든** 그 북의 만기일이다 | 그 북 (요일 무관) | 만기 당일 거래량은 다른 모든 규칙을 압도한다 |
| 2 | 먼슬리 만기가 속한 주(週)의 **화·수·목** | `regular` | 먼슬리 쏠림은 화요일부터 시작해 만기일(주로 목)에 정점 |
| 3 | 그 외 **화·수·목** | `weekly_thu` | |
| 4 | **금·월** | `weekly_mon` | |

### 1-1. 규칙 1 — 만기 당일 최우선

**왜 필요한가**: 2026-08-18(화) 실측 — 원래 위클리 월 만기는 08-17(월)인데 그날이 대체공휴일
이라 만기가 화요일로 밀렸다. 규칙 3(화=weekly_thu)을 그대로 적용했다면 목표가 틀렸을 것이다.
실측 거래량은 weekly_mon 1,184,054 대 weekly_thu 15,843 — **75배 차이.** 만기 당일은 요일
규칙보다 강한 별개의 힘이다.

**판정 방법**: 그날 관측된 각 북의 `expiry` 값이 오늘 날짜와 같은지 본다(달력을 별도로 계산
하지 않는다 — 마흐디 자신이 관측한 값을 쓴다. `instrument_selection.is_expiry_day()`와
같은 원칙, "요일 규칙으로 만들지 않는 이유" 참고).

### 1-2. 규칙 2 — 먼슬리 마지막주는 화요일부터

**왜 월요일이 빠지는가**: 2026-08-10(월, 먼슬리 만기 08-13 목이 속한 주의 첫날) 실측 —
`regular` 21,800 대 `weekly_mon` 768,915. 아직 무게중심이 넘어오지 않았다. 그 뒤 흐름:

| 날짜 | regular 거래량 |
|---|---|
| 08-10(월) | 21,800 |
| 08-11(화) | 68,847 |
| 08-12(수) | 202,339 |
| 08-13(목, 만기일) | 852,214 |

화요일부터 매일 눈덩이처럼 불어나 만기일에 정점을 찍는다. **월요일은 규칙 4(금·월→weekly_mon)에
그대로 맡긴다** — 별도 예외를 안 둬도 이미 맞는 답이 나온다.

**"먼슬리 만기가 속한 주"의 정의**: 오늘과 `regular` 북의 `expiry`가 같은 ISO 주(월~일)에
속하는가(`date.isocalendar()[:2]`가 같은지 비교). 요일 기반 근사가 아니라 실측 만기일 기준이다.

### 1-3. 규칙 3·4 — 기본 요일 규칙

가장 단순한 축이다. 화·수·목은 weekly_thu, 금·월은 weekly_mon. 위클리 목/월이 각각
목요일/월요일에 만기이므로, **만기까지 남은 요일 구간 동안 그 북에 거래가 몰린다**는
시장 미시구조의 상식적인 결과다(위클리 만기가 다가올수록 그 주의 위클리로 활동이 수렴).

## 2. 옵션체인 수집(collection)에 적용 — 무엇을 바꾸고 무엇을 바꾸지 않는가

**중요한 구분**: 이 문서의 규칙은 **"어느 북에서 진입 후보를 고를 것인가"**(선택기 문제)를
답한다. **"어느 북을 먼저 수집할 것인가"**(수집 예산 배분 문제)는 별개의, 이미 존재하는
관심사이고 — 이 규칙으로 대체하면 안 된다.

### 2-1. 바꾸지 않는 것 — 먼슬리는 계속 수집 우선순위 최상위

`mahdi/main.py`의 옵션체인 수집 루프(§2-6/Fix#8, 실패 예산 §2026-08-11 고도화 A)에서
먼슬리(`regular`) 10레그는 **요일과 무관하게 항상 `is_priority=True`**로 유지한다.
GEX·감마플립은 먼슬리 북에서만 계산되고(§11.4), 이것은 판단 엔진 전체의 입력이지
특정 요일의 거래 대상이 아니다. **레짐/감마플립 계산용 수집 우선순위와 "오늘 무엇을
거래할 것인가"는 다른 질문**이며, 이 문서는 후자만 다룬다.

동작점검 §1(2026-08-18 14:30 회차)에서 확인한 `우선순위위반=예`(14:05·14:06) 버그 수정도
이 우선순위(수집)를 대상으로 한다 — 이 문서의 규칙과는 별개 트랙이다. 서로 이름이
헷갈리지 않도록 앞으로 "수집 우선순위"(collection priority, 먼슬리 고정)와 "거래 목표북"
(trading target series, 이 문서의 요일 로테이션)을 구분해 부른다.

### 2-2. 바뀌는 것 — 종목 선택기가 참조하는 북

`mahdi/fusion/instrument_selection.py` `select_book()`이 지금은:

```python
future = [expiry for expiry in observed_expiries(legs) if expiry > today]
return future[0], None   # 가장 가까운 만기 — 요일/거래량 무관
```

이것을 **§1의 4단계 우선순위**로 교체한다. 함수 시그니처는 만기일뿐 아니라 series 문자열도
반환해야 한다(현재는 `date`만 반환하고 series는 그 만기에 해당하는 레그에서 역산하는 구조이므로,
"이번엔 어느 series를 볼 것인가"를 먼저 정하고 그 series의 만기를 채택하는 순서로 뒤집는다).

**의사코드**:

```python
def target_series_for(today: date, observed_expiries_by_series: dict[str, date]) -> str:
    # 1. 만기 당일 최우선
    for series in ("regular", "weekly_mon", "weekly_thu"):
        if observed_expiries_by_series.get(series) == today:
            return series

    # 2. 먼슬리 마지막주(화~목)
    regular_expiry = observed_expiries_by_series.get("regular")
    weekday = today.weekday()  # 0=월 ... 4=금
    if (regular_expiry is not None
            and today.isocalendar()[:2] == regular_expiry.isocalendar()[:2]
            and weekday in (1, 2, 3)):
        return "regular"

    # 3·4. 기본 요일 규칙
    if weekday in (1, 2, 3):
        return "weekly_thu"
    if weekday in (4, 0):
        return "weekly_mon"
    return "n/a"  # 주말 — 거래일이 아니므로 애초에 호출되지 않는다
```

`select_book()`은 이 `target_series_for()`가 돌려준 series의 만기를 찾아 반환한다. 그 series가
그날 체인에 아예 관측되지 않았으면(수집 실패 등) 기존처럼 `REASON_NO_ELIGIBLE_BOOK`으로
후퇴한다 — **목표북이 없다고 다른 북으로 조용히 넘어가지 않는다.** 조용히 넘어가면 "오늘
왜 그 북을 안 골랐는가"가 로그에서 사라진다(규약 C와 같은 원칙).

## 3. 로깅 — 목표북과 실제 거래량 1위가 갈리면 반드시 남긴다

`select_book()` 호출부(또는 `signal_decisions` 적재 지점)에 다음을 기록한다:

- `target_series`(이 규칙이 고른 값)
- `target_series_reason`(1/2/3/4 중 어느 순위에서 결정됐는지)
- 가능하면 그 분의 관측 거래량 1위 series(사후 검증용 — 목표와 실측이 자주 어긋나면 규칙이
  낡았다는 신호)

이것이 없으면 다음 번 이 규칙이 틀렸을 때(예: 다음 달 먼슬리 만기 주가 이번과 다르게 움직일
때) 사람이 손으로 이틀치 로그를 겹쳐 읽어야 한다 — 동작점검 문서들이 반복해서 지적하는
그 실패 패턴이다.

## 6. 구독 창 확장 파일럿 — 델타 0.2~0.3 도달 문제를 실측으로 닫는다

### 6-0. 왜 과거 데이터로는 답이 안 나왔는가 (요약)

`verify_weekly_delta_reach.py` v1(포인트 거리)·v2(변동성 표준화 거리 z)를 둘 다 돌려봤다.
v2는 weekly_mon 풋 한 날개(R²=0.917)만 신뢰할 만했고, 나머지 세 날개는 회귀가 무너졌다
(R² 0.686 / 0.118 / 0.006). 원인은 통계 기법이 아니라 **원본 데이터 자체**였다 —
`RollingSubscriptionManager`의 창은 설계상 ATM±2(5개 행사가, 편측 최대 5.0포인트)인데,
2026-08-04 이전엔 "WS 연결당 1회만 롤링"해 창이 스팟을 못 따라가는 날이 있었다(하루치
체인이 5.5% 외가격으로 방치된 사례가 실제로 있었다). 지금 관측되는 z=1~2대(스팟에서
100~240포인트)의 값들은 **설계된 넓은 관측이 아니라 그 낙오 구간의 우연한 스냅샷**이라
델타가 안정적이지 않다(0.484 같은 특정 값이 서로 다른 z 구간에 그대로 반복되는 것이 그 증거).

**결론: 과거 데이터를 더 파도 안 나온다. 창을 실제로 넓혀서, 안정적으로 굴러가는 상태에서
며칠 직접 수집해야 한다.** 아래가 그 파일럿 설계다.

### 6-1. 새로 확인한 제약 — WS 구독 슬롯 41개 상한

이건 지금까지 얘기한 REST 수집 예산(50초/사이클)과 **다른, 별개의 하드 리밋**이다.
`mahdi/main.py:4388` 주석에 이미 실측 계산이 있다:

```
3북(먼슬리+위클리 월+위클리 목) × ATM±2(10슬롯) + 선물 1 = 31 / 41
ATM±3(14슬롯)으로 3북 전부 넓히면 3×14+1 = 43 → 한도 초과, 실제로 시도했다가 되돌렸다
(RESEARCH_EXPIRY_SELECTION_v1.md §3.1, 사용자 확인 후 결정, [[DECISION_LOG]] 참고)
```

`poll_option_chain()`의 REST 레그도 `subscription_manager.desired_strikes`를 그대로 쓰므로
(main.py:1954), **WS 구독 창을 넓히지 않고는 REST로도 더 못 본다** — 이 둘은 같은 상태를 공유한다.

**그런데 이번엔 세 북을 똑같이 넓히자는 게 아니다.** 요일 로테이션 규칙(§1)으로 그날 실제로
쓰이는 건 목표 위클리 하나뿐이니, **목표 위클리만 비대칭으로 넓히면** 계산이 달라진다:

| 시나리오 | 슬롯 계산 | 여유 |
|---|---|---|
| 지금(3북 모두 ATM±2) | 10+10+10+1 | 31/41, 여유 10 |
| **목표 위클리만 ATM±3(14슬롯)** | 10(먼슬리)+10(비목표 위클리)+14(목표)+1 | **35/41, 여유 6** ✅ |
| 목표 위클리만 ATM±4(18슬롯) | 10+10+18+1 | **39/41, 여유 2** — 빠듯함 |

**ATM±3을 1차 목표로 삼는다.** 이미 2북 체제(2026-07 이전)에서 실제로 썼던 값이고
(`RESEARCH_EXPIRY_SELECTION_v1.md`: "2개 북×ATM±3=28+1=29 ✅"), 여유 6슬롯이면 재연결
과도기의 일시적 중복 구독도 흡수할 수 있다. ATM±4는 §6-4에서 실측 후 필요하면 2차로 검토한다.

### 6-2. REST 시간 예산도 같이 맞춘다 — 여기서 먼슬리 절충안이 실제로 쓰인다

ATM±2→ATM±3은 레그가 10→14로 **+4레그**(콜·풋 각 2행사가 추가). 지난 대화의 먼슬리
절충안(§비목표일엔 IV용 소수 레그만 매분, 나머지는 저빈도)이 여기서 그 +4레그의 시간을
메운다 — 새로 REST 총량을 늘리는 게 아니라, 먼슬리에서 줄인 만큼 위클리로 옮기는 것이다.

**단, 이 절충안 자체가 아직 미검증이다**(지난 턴에서 "코드 확인 필요"로 남겼다). 파일럿
1주 차는 **절충안 없이, 그냥 REST 총 레그가 24개(먼슬리 10 + 목표 위클리 14)로 늘어난
채로** 돌려서 예산 초과가 실제로 얼마나 나는지부터 잰다. 그 실측이 절충안의 필요성을
숫자로 확정해준다 — 순서를 먼저 넓히기 → 문제 확인 → 절충안 적용, 으로 둔다(추측으로
먼저 두 가지를 한꺼번에 바꾸면 무엇이 원인인지 나중에 못 가른다).

### 6-3. 파일럿 전에 반드시 먼저 할 것 — 창 고착 여부를 스스로 재는 계측

§6-0의 실패가 반복되지 않으려면, **창이 스팟을 실제로 따라가고 있는지 파일럿 기간 내내
스스로 재야 한다.** 새 계측 하나만 추가한다(코드 변경 최소, 읽기 전용):

```
매 사이클: |스팟 - 목표 위클리 창의 중심 행사가| 를 로그에 남긴다
경고: 그 값이 strike_interval * ATM_ROLL_HYSTERESIS_RATIO(2.5*0.75=1.875)를 넘겼는데
      다음 사이클에도 안 줄어들면 — 롤링이 걸려야 하는데 안 걸린 것 — WARNING
```

이건 §6 파일럿 전용이 아니라 **상시 켜둘 가치가 있는 진단**이다 — 08-04 이전 사고가
지금 재발했는지 여부를 실시간으로 답해준다. 이 계측 없이 파일럿을 돌리면, 나중에 델타
곡선이 또 이상하게 나왔을 때 "창이 넓어서 그런지, 또 고착돼서 그런지" 못 가른다.

### 6-4. 파일럿 실행 계획

| 단계 | 내용 | 기간 |
|---|---|---|
| 0 | §6-3 창 고착 계측 추가·배포 | 파일럿 시작 전 1일 |
| 1 | 목표 위클리만 ATM±3로 확대(레버로, 아래 §6-5). REST 총 레그 24개 상태로 관찰 | 위클리 월·목 각 1사이클(최소 5거래일, 화~목+금~월 걸치도록) |
| 2 | 1단계 로그로 REST 예산 초과 실측 → 초과가 유의미하면 먼슬리 절충안(§비목표일 IV-lite) 적용 | 1단계 직후 |
| 3 | `verify_weekly_delta_reach.py` v2를 **이번엔 진짜 넓은 창의 실측 데이터**로 재실행 — 델타 0.2~0.3 도달률, R², 그리고 **`spread_state`(호가 존재 여부)** 까지 같이 확인 | 1단계 완료 후 |
| 4 | Go/No-Go — 도달률이 유의미하게 올랐고 호가도 있으면 확대를 상설화, 아니면 되돌린다 | 3단계 직후 |

3단계에서 스프레드 상태를 반드시 같이 보는 이유는 §1에서 이미 짚었다 — **델타가 관측된다고
거래 가능하다는 뜻은 아니다.** 넓힌 창에 잡힌 행사가가 정말 호가가 있는 살아있는 옵션인지,
아니면 여전히 죽은 시세인지는 이번에 처음으로 직접 확인할 수 있다.

### 6-5. 레버로 만든다 — 조용히 영구화되지 않도록

마흐디의 기존 관례(동작점검 §7 "레버 상태" — 무조건발동일 없는 레버는 유예가 조용히
영원해진다)를 그대로 따른다. `strategy_params.yaml`에:

```yaml
weekly_window_pilot:
  enabled: true
  target_series_strikes_each_side: 3   # 기본 2에서 파일럿 기간만 3
  pilot_end_date: 2026-08-29            # 무조건발동일 — 이 날짜가 지나면 자동으로 꺼진다
```

파일럿 종료일을 코드가 아니라 날짜로 박아두면, §6-4의 Go/No-Go 판단을 사람이 깜빡해도
자동으로 원상복귀한다 — 동작점검이 반복 지적한 "결정된 유예가 아니라 잊힌 유예" 패턴을
여기서는 처음부터 막는다.

### 6-6. 롤백 조건 — 파일럿 중이라도 즉시 되돌리는 경우

- §6-3 계측이 창 고착(WARNING)을 **1회라도** 잡으면 그날 데이터는 분석에서 제외하고,
  3회 이상 반복되면 파일럿을 중단하고 롤링 로직 자체를 먼저 고친다(수집 폭을 넓혀도
  고착 문제가 안 풀리면 의미가 없다).
- WS 슬롯이 41을 넘기는 순간(재연결 과도기 등)이 관측되면 즉시 ATM±3→ATM±2로 되돌린다.
- REST 예산 초과(`budget_exceeded`)가 파일럿 이전 대비 **눈에 띄게** 늘면(예: 시간대별
  비율이 기존 §5-1 게이지의 경고선 0.8을 넘기면) 2단계(절충안)를 앞당겨 적용한다.
