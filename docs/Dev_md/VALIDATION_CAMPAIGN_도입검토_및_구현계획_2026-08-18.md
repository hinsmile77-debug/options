# 검증 캠페인(Validation Campaign) 도입 검토 및 구현계획

**작성 2026-08-18 · [MW0601] · 대상: 마흐디(options)**
**참조 원본: 미륵이(futures) `config/settings.py:VALIDATION_CAMPAIGN` ·
`scripts/generate_validation_campaign_report.py` · `CLAUDE.md` §검증 캠페인 운영 모드**

---

## 결론

**도입한다. 다만 미륵이의 코드가 아니라 제도만 가져온다.**

미륵이의 판정 생성기는 11,074줄이고 470여 세션에 걸쳐 자란 것이다. 마흐디에 필요한 것은
그 규모가 아니라 **두 개의 빈자리**다:

1. **표본이 찰 때까지 판정을 미루는 자리** — 지금 마흐디에는 「아직 모른다, 계속 쌓는 중」을
   **지속적으로** 표현할 곳이 없다.
2. **결정을 판정과 분리해 기억하는 자리** — 「이건 일부러 안 했다」를 코드가 기억하는 곳이 없다.

그리고 **누적 인프라는 이미 있다.** 일별 지표가 `docs/동작점검/auto/YYYY-MM-DD_지표.json`에
커밋되는 위치로 매일 쌓이므로, 캠페인 판정기는 그 파일들을 읽어 접기만 하면 된다.
새 수집 경로·새 테이블·새 폴러가 필요 없다 — 이것이 도입 비용을 결정적으로 낮춘다.

## §1. 미륵이가 하고 있는 것

**채널(channel)** = 하나의 열린 질문. **67개**가 상시 가동 중이다. 각 채널은 데이터를 보기 전에
합격선을 `VALIDATION_CAMPAIGN`에 고정한다(사전등록).

```python
"hurst_gate_shadow": {
    "min_samples": 20,      # 차단 건 최소 수 (미달 -> 판정 보류)
    "cf_window_min": 30,
},
```

매주 금요일 EOD 체인이 판정 리포트를 생성하고, 채널별로 **`min_samples`에 도달한 시점에
개별 판정**한다. 기한은 없다 — 2026-08-01에 「4주 캠페인」에서 **상시(standing)** 로 전환했다.
전환 이유가 그대로 마흐디에 적용된다:

> `min_samples=20`짜리 채널 다수가 실측 도달속도 기준 **9~16주 스케일**이다.
> "W4에 활성화/폐기를 확정한다"는 전제가 표본 현실과 맞지 않았다.

### 이 제도의 진짜 발명 — 판정(verdict)과 결정(decision)의 분리

리포트의 판정은 **조치 여부와 무관하게 매주 재계산·재출력**된다. 따라서 "FAIL이 계속 뜬다"가
"미조치"를 뜻하지 않는다. 미륵이는 양방향 사고를 **둘 다 실제로 겪었다**:

- **이미 이행된 권고를 신규 안건으로 오인** — Hurst 완화는 배포돼 라이브 중인데 리포트가
  3주째 같은 권고를 찍었고, 주간 결산 초안이 그것을 "승인 1순위"로 잘못 올렸다(코드 확인 후 철회).
- **일부러 적용하지 않기로 한 FAIL이 기록되지 않음** — 다음 세션이 같은 FAIL을 보고 적용을
  재시도할 위험.

→ `VALIDATION_CAMPAIGN_DECISIONS`(확정 결정 레지스트리)를 두고, 리포트가 요약표에
**📌 인라인 마커** + 하단 레지스트리 섹션으로 렌더링한다.

### 판정 상태가 다치(多値)다

`PASS` / `FAIL` / `INSUFFICIENT`(표본 미달) / `OBSERVE`(임계 없이 관측) / `SUPPORTS_GATE` /
`ALERT_*`. **`INSUFFICIENT`가 일급 상태라는 것이 핵심이다** — "하루치로 결론 내지 않는다"를
사람의 자제력이 아니라 **자료구조**로 강제한다.

### 산출물 규약

```
docs/정기점검/금요일점검/<PC명>/validation_campaign_report_YYYYMMDD.md
```

두 사고를 막기 위한 규약이고 **둘 다 실제로 발생했다**: (1) 산출물이 gitignore 위치라 다른 PC
리포트를 볼 수 없었다 → 커밋되는 위치로 옮겼다(런타임 산출물 커밋 금지의 **의도적 예외**).
(2) 고정 파일명이 매주 덮어써서 지난주 리포트를 잃었다 → **날짜본, 절대 덮어쓰지 않는다.**

## §2. 마흐디에 이미 있는 것 / 없는 것

### 이미 있다 — 다시 만들지 않는다

| 자산 | 무엇 |
|---|---|
| `docs/동작점검/hypotheses.yaml` (93건) | **사전등록.** 숫자를 보기 전에 예측을 적는 규약 |
| `mahdi/ops/hypotheses.py` | 역할(주장/대가/참고) · 규약 A~H · 자동 판정 |
| `tests/test_ops_hypotheses.py` | **지표 경로가 자동 집계에 없으면 막는다** — 「영원히 검정 불가한 가설」 방지 |
| `docs/동작점검/auto/YYYY-MM-DD_지표.json` | **일별 지표가 커밋 위치에 매일 쌓인다** |
| `mahdi/ops/report.py` §0-1 | 가설 검정 표를 매일 인쇄 |
| `scripts/daily_ops_report.py` | EOD 체인 |

**마흐디는 사전등록을 이미 하고 있다.** 미륵이가 `VALIDATION_CAMPAIGN`으로 하는 일의 절반을
`hypotheses.yaml`이 이미 한다. 규약 F(주장 지표를 절대 건수로 세우지 않는다)·규약 G(시장 상태
의존 지표에 무조건부 하한 금지)는 **미륵이에 없는 마흐디 고유 자산**이기도 하다.

### 없다 — 이것이 도입 대상이다

**① 누적(accumulation)이 없다.** `hypotheses`의 수명은 `구현일 → 검증예정일 → 상태`다.
검증예정일이 **단일 날짜**이고 그날 판정한다. `min_samples`라는 개념이 `hypotheses.py`에
**0회** 등장한다. 표본이 며칠~몇 주 걸리는 질문을 담을 자리가 없다.

**② 「아직 모른다」의 지속 상태가 없다.** 현재 상태값은
`pending / confirmed / refuted / inconclusive / untested`인데, `pending`은 "검증예정일이 안
왔다"이고 `inconclusive`는 "그날 보고 판정 못 했다"로 **종결된** 상태다.
「계속 쌓는 중, N/M 도달」을 매일 갱신하며 유지하는 상태가 없다.

**③ 결정 레지스트리가 없다.** 「이 FAIL은 일부러 적용하지 않기로 했다」가 코드에 없다.
지금은 `DECISION_LOG.md` 산문에만 있고 **자동 리포트는 그것을 모른다.**

**④ 판정 상태가 이치(二値)에 가깝다.** `확인/반증` 중심이고 `OBSERVE`가 개념으로만 존재한다 —
규약 G가 *"임계 없이 인쇄만 한다"* 를 반복해 쓰는데 **그 상태에 이름이 없어** 매번 산문으로 적는다.

## §3. 왜 지금인가 — 오늘 p1이 실증했다

2026-08-18 판정에서 `2026-08-17-p1`이 반증됐다(후보율 19.5% vs 예측 ≥ 90%). 원인은 규명됐다 —
`small_strangle_buy`가 요구하는 |델타| 0.20~0.30이 구독 창(ATM±N) 밖이고, 08-20 북 실측에서
풋 밴드 보유율이 **6.2%** 였다.

그리고 후속이 셋으로 갈렸다:

```
(a) 구독 창을 넓힌다          REST 예산 실비용 (예산 컷 이미 71건)
(b) 밴드를 관측 가능 범위로   그 숫자가 곧 전략의 정의가 된다
(c) 계측 불가로 기록하고 둔다
```

**이 결정은 하루치로 내릴 수 없다.** 그런데 **지금 이 질문이 살 곳이 없다**:

- `hypotheses.yaml`에 넣으면 검증예정일을 정해야 하고, 그날 표본이 안 차 있으면
  `inconclusive`로 종결되거나 매일 날짜를 미루게 된다.
- `NEXT_TODO.md`에 체크박스로 넣으면 **아무도 표본을 세지 않는다** — 다음 세션이 그냥 (a)를
  하거나, 아니면 잊는다.
- 미륵이가 겪은 두 사고가 **정확히 이 형태로** 마흐디에 예약돼 있다.

마흐디에도 같은 형태의 전례가 이미 있다. 레버 E는 *"발동 조건이 이미 네 번 성립했고 네 번
미뤘다"* 로 기록돼 있고, **그 네 번을 세는 자리가 없어 매번 산문으로 다시 세었다.**

## §4. 도입 범위 — 가져오는 것과 안 가져오는 것

### 가져온다

1. **채널** — 열린 질문 하나 = 채널 하나. 합격선·`min_samples` 사전등록.
2. **`INSUFFICIENT`를 일급 상태로** — N/M 진행률과 함께 매일 인쇄.
3. **결정 레지스트리 + 📌 마커** — 판정과 결정의 분리.
4. **상시(standing) 운영** — 기한 없음, 채널별 개별 판정.
5. **날짜본 산출물, 덮어쓰기 금지.**

### 가져오지 않는다

| 안 가져오는 것 | 왜 |
|---|---|
| 11k줄 판정 생성기 | 채널마다 전용 판정 로직을 쓴 결과다. 마흐디는 **지표 경로 + 비교 연산자**로 시작한다 |
| 주간(금요일) 주기 | 마흐디는 **일일 리포트**가 이미 EOD 체인이다. 캠페인 절을 거기 붙인다 — 새 스케줄러 없음 |
| PC별 폴더 | 마흐디는 단일 PC 운영이다. 필요해지면 그때 |
| 별도 산출물 파일 | 일일 리포트 **§0-2 절**로 넣는다. 파일이 늘면 아무도 안 읽는다 |
| 합격선을 코드(`settings.py`)에 두는 것 | 마흐디는 사전등록을 `docs/동작점검/`에 둔다(`hypotheses.yaml` 선례). **한곳에 모은다** |

**핵심 판단**: 미륵이는 캠페인을 *새 축*으로 세웠지만, 마흐디는 **`hypotheses.yaml`의 확장**으로
낸다. 사전등록·역할·규약 A~H·지표 경로 검증이 이미 있으므로 그 위에 «누적»만 얹는 것이 새 축을
세우는 것보다 싸고, 두 축이 갈려 서로 다른 사실을 말할 위험도 없다(규약 A).

## §5. 설계

### 5-1. 파일 — `docs/동작점검/validation_campaign.yaml` (신설)

`hypotheses.yaml` 옆에 둔다. 두 최상위 키.

```yaml
channels:
  - id: "strangle-delta-band-reach"
    개시일: 2026-08-19
    질문: "small_strangle_buy가 요구하는 |델타| 0.20~0.30이 구독 창 안에 얼마나 들어오는가"
    배경: |
      2026-08-17-p1 반증의 후속. 08-18 실측에서 08-20 북 풋 밴드 보유율 6.2%.
      (a)창 확대 / (b)밴드 재정의 / (c)계측 불가 기록 중 하나를 고르는 근거를 쌓는다.
    표본:
      metric: db.decisions.selected_instruments.enter_minutes   # 표본을 세는 경로
      min_samples: 1000                                         # 도달 전 INSUFFICIENT
      min_days: 10                                              # 단일일 쏠림 방지
    판정:
      - metric: db.decisions.selected_instruments.reason.no_strike_match
        rule: "비율 < 0.30"
        역할: 주장
    상태: open        # open | judged | closed
    결정: null        # 확정되면 decisions의 id

decisions:
  - id: "strangle-band-axis"
    date: 2026-08-??
    channel: "strangle-delta-band-reach"
    decision: "..."
    근거지표: db.decisions.selected_instruments.reason.no_strike_match
    note: "왜 그렇게 정했는가 — 되돌리려면 무엇이 바뀌어야 하는가"
```

### 5-2. 판정 상태 — 마흐디 기존 상수와 충돌하지 않게

| 상태 | 뜻 | 마흐디의 기존 대응 |
|---|---|---|
| `INSUFFICIENT` | 표본 미달. **N/M과 함께 인쇄** | (없음 — 신규) |
| `PASS` / `FAIL` | 합격선 대비 판정 | `확인` / `반증` |
| `OBSERVE` | 임계를 일부러 안 걸었다 | **규약 G** — 지금은 산문으로만 |
| `BLOCKED` | 전제 채널이 아직 미판정 | (없음 — 신규) |

`INSUFFICIENT`가 **FAIL이 아니라는 것**이 요점이다. 오늘 p1이 겪은 일 — 표본은 충분했는데 예측
근거가 구조 변수를 빠뜨린 것 — 과 「표본이 아직 없다」는 완전히 다른 사건이고, 지금 마흐디는
둘 다 `inconclusive`로 뭉갠다.

### 5-3. 누적 — 새 인프라 없음

판정기는 `docs/동작점검/auto/*_지표.json`을 **개시일 이후 전부** 읽어 지표 경로를 접는다.
그 파일들은 이미 매일 생성되고 커밋된다. 필요한 것은 «접는 함수»뿐이다.

⚠ **한 가지 제약**: 채널이 지목하는 지표 경로는 **개시일 이전 파일에는 없을 수 있다**
(오늘 신설한 `db.decisions.selected_instruments`가 그렇다). 없는 날은 «그날은 못 쟀다»로
세고 표본에 넣지 않는다 — **0으로 채우면 규약 C 위반이다.**

### 5-4. 리포트 — 일일 §0-2 절 신설

§0-1(가설 검정) 바로 아래. 요약표는 미륵이 형식을 따르되 **진행률**을 넣는다.

```
| 채널 | 판정 | 진행 | 핵심 수치 |
|---|---|---|---|
| [C1] 스트랭글 델타밴드 도달 | ⏳ INSUFFICIENT | 203/1000 (2일) | no_strike_match 81.3% |
| [C2] 단축코드 해결률       | 👁 OBSERVE      | 80/— (1일)      | 100.0% — 임계 없음(규약 G) |
```

📌 마커는 §0-1이 이미 쓰는 렌더링 방식을 그대로 재사용한다.

### 5-5. 강제 장치 — 마흐디식으로

미륵이에는 없고 마흐디에는 있는 것을 **캠페인에도 적용한다**:

- `test_ops_hypotheses.py`가 지표 경로를 검증하듯, **채널의 지표 경로도 자동 집계에 있어야
  한다** — 없으면 테스트가 막는다. 「영원히 검정 불가한 채널」을 만들지 않는다.
- 규약 F(주장 지표를 절대 건수로 세우지 않는다)를 **채널 판정 규칙에도 적용**한다.
- 규약 G에 걸리는 지표는 `OBSERVE`로만 등록할 수 있게 한다(임계를 못 걸게).

## §6. 구현 계획

### Phase 1 — 뼈대 (1세션 · 코드 ~400줄 + 테스트)

- [ ] `docs/동작점검/validation_campaign.yaml` 신설 — 스키마 + 초기 채널 2개(§7).
- [ ] `mahdi/ops/campaign.py` — 로드·검증·누적·판정. `hypotheses.py`의 구조를 그대로 따른다
      (상수 → 순수 함수 → 판정). **DB를 직접 읽지 않는다** — 일별 json만 읽는다.
- [ ] `mahdi/ops/report.py` §0-2 절 + 📌 렌더링.
- [ ] `tests/test_ops_campaign.py` — 스키마 검증 · 지표 경로 존재 · 규약 F/G 적용 ·
      `INSUFFICIENT`가 표본 미달에서만 나오는지 · 결정 마커 렌더링.

**완료 기준**: 오늘의 (a)/(b)/(c) 질문이 채널로 등록되고, 내일 리포트가
`INSUFFICIENT 203/1000`을 인쇄한다.

### Phase 2 — 결정 레지스트리 (Phase 1 다음 세션)

## §8. 비용과 위험

**비용**: 코드 ~400줄 + 테스트. 새 폴러·새 테이블·새 스케줄러 **없음**. 일일 리포트가 한 절
길어진다.

**위험 1 — 축이 둘로 갈린다.** `hypotheses.yaml`과 `validation_campaign.yaml`이 서로 다른
사실을 말할 수 있다(규약 A 위반). → **경계를 명문화한다**: 하루 뒤 판정할 수 있으면 가설,
표본이 필요하면 채널. 채널이 종결되면 결과를 가설로 이관하고 채널은 닫는다.

**위험 2 — 채널이 방치된다.** 미륵이는 67개를 운영하는데 그중 다수가 `INSUFFICIENT`로 몇 달째다.
→ **Phase 1은 2개로 시작**하고, 표본 기아 경보(Phase 3) 전에는 5개를 넘기지 않는다.

**위험 3 — 결정 레지스트리가 낡는다.** 미륵이가 실제로 겪은 사고다(431차 — 무효화된 수치가
3일간 사이징 축을 봉쇄). → 결정 항목에 **근거지표 경로**를 함께 적어 무효화를 감지하게 한다(Phase 2).

## §9. 하지 않을 것

- **미륵이 판정기를 이식하지 않는다.** 채널별 전용 로직 11k줄은 그 프로젝트의 역사다.
- **주간 별도 리포트를 만들지 않는다.** 일일 리포트 한 절로 낸다.
- **채널을 한꺼번에 열지 않는다.** 2개로 시작한다.
- **오늘의 (a)/(b)/(c)를 지금 고르지 않는다.** 이 제도를 만드는 이유가 그것이다.
